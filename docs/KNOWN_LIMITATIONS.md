# Integration limits and remaining work

- **Social links:** only publicly retrievable HTML/structured recipe data is attempted. Instagram/TikTok authentication, private posts, platform restrictions, carousel APIs, and direct social video downloads are not bypassed or implemented. Uploaded screenshots/video and pasted captions are the supported fallback.
- **OCR:** English only initially; exact line overlap is deduplicated. OCR accuracy depends on resolution/layout. Similar-but-not-identical duplicates and subtle quantity conflicts require user review. There is no reliable recipe extraction from a finished-food photo alone.
- **Video:** optional Python/faster-whisper model and FFmpeg must be installed. CPU mode is the default; GPU setup is not automated. Sampling every 15 seconds can miss brief text. Videos over 10 minutes/250 MB are rejected. Drag-and-drop currently handles images; use the native file picker for video.
- **Model grounding:** schema validation and explicit suggestion labels reduce risk but cannot guarantee that a local LLM never hallucinates. Compare suggestions with evidence before saving. AI is optional; conservative text/JSON-LD parsing works without a model.
- **Multi-recipe sources:** each import presents one main review draft while retaining competing source evidence. Selection can be ambiguous; check the chosen recipe. Import unrelated recipes separately.
- **Nutrition:** matching is user-driven. No LLM nutrient guesses, automatic density guesses, oil-absorption estimates, or photo-only weights. USDA energy records that use unsupported nutrient IDs/units remain unknown. Source nutrition basis must be confirmed. Food cache entries retain retrieval timestamps; a refresh/invalidation UI is future work.
- **Media:** direct website imports select a likely dish photo using metadata and page structure. This is not visual food recognition and can be wrong or unavailable. Change/remove the cover during review. Saved browser files remain offline and need manual covers; existing recipes are not backfilled. Profile avatars use initials. Automatic media-retention schedules are not implemented.
- **Editing:** additional evidence is attached without automatically merging ingredient/step changes. Ingredient groups are supported, but there is no group drag-and-drop UI. Reordering uses keyboard-accessible buttons. Source wording is retained when quantities are scaled; current measurements are shown separately.
- **Durability:** saved recipe cards and completed/partially recovered import evidence persist. An unsaved editor session is not yet autosaved; save a draft before closing. A close-confirmation workflow guards dirty editors.
- **Backups:** JSON/base64 backups are intended for modest libraries; restore rejects files above 400 MB. Large streaming archives and crash-resume during file copying are future improvements. Exported single-recipe JSON is portable but is not a full backup with embedded images.
- **Performance:** synchronous SQLite writes and JSON backup creation run in the main process. They are appropriate for an initial personal library, but very large libraries need streaming backup and repository workers.
- **Platform:** Windows-first. macOS installer configuration, mobile clients, cloud synchronization, automatic updates, global share-sheet integration, and secure online accounts are not part of this MVP.
- **Setup:** tool status and opt-in controls live in Settings. Large local-model installations are documented/manual rather than silently installed. Runtime OCR/transcription/model/USDA verification depends on connectivity and user setup; see TEST_RESULTS.md for what was actually tested.

User preference questions were presented before implementation. With no selections returned, the build uses the prompt's warm visual grid, local processing, SQLite, optional USDA, and modest CPU-oriented defaults. No paid plan, hosted project, credential, or large AI model was activated.
